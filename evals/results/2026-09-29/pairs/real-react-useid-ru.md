<Intro>

Хук `useId` создаёт уникальные идентификаторы, например для атрибутов доступности.

```js
const id = useId();
```

</Intro>

## Справочник {/*reference*/}

### `useId()` {/*useid*/}

Чтобы создать уникальный идентификатор, вызовите `useId` на верхнем уровне компонента:

```js
import { useId } from 'react';

function PasswordField() {
  const passwordHintId = useId();
  // ...
```

[См. другие примеры ниже.](#usage)

#### Параметры {/*parameters*/}

`useId` не принимает параметров.

#### Возвращаемое значение {/*returns*/}

Строку — уникальный идентификатор. Он привязан к конкретному вызову `useId` в конкретном компоненте и не меняется между рендерами.

#### Замечания {/*caveats*/}

* `useId` — хук. Вызывайте его только **на верхнем уровне компонента** или собственного хука. В циклах и условиях вызывать нельзя: вынесите вызов в отдельный компонент и рендерите его по условию или в цикле.

* Сейчас `useId` нельзя использовать в [асинхронных серверных компонентах](/reference/rsc/server-components#async-components-with-server-components).

* Не используйте `useId` для ключей в списках. [Ключи должны выбираться на основе данных.](/learn/rendering-lists#where-to-get-your-key)

* При [серверном рендеринге](/reference/react-dom/server) деревья компонентов на сервере и на клиенте должны быть идентичными. Иначе идентификаторы, созданные на сервере, не совпадут с клиентскими.

---

## Применение {/*usage*/}

### Идентификаторы для атрибутов доступности {/*generating-unique-ids-for-accessibility-attributes*/}

Вызовите `useId` на верхнем уровне компонента и укажите <CodeStep step={1}>полученный идентификатор</CodeStep> в нужных атрибутах:

```js [[1, 2, "passwordHintId"], [1, 5, "passwordHintId"], [1, 6, "passwordHintId"]]
function PasswordField() {
  const passwordHintId = useId();
  return (
    <>
      <input type="password" aria-describedby={passwordHintId} />
      <p id={passwordHintId}>Пароль должен содержать не менее 18 символов</p>
    </>
  );
}
```

[Атрибуты доступности](https://developer.mozilla.org/ru/docs/Web/Accessibility/ARIA), такие как [`aria-describedby`](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Attributes/aria-describedby), обозначают смысловую связь между элементами. Например, абзац может быть кратким описанием поля ввода.

В обычном HTML эту связь описывают фиксированным идентификатором:

```html {5,8}
<label>
  Пароль:
  <input
    type="password"
    aria-describedby="password-hint"
  />
</label>
<p id="password-hint">
  Пароль должен содержать не менее 18 символов
</p>
```

В React так делать не стоит. Один компонент может отображаться в нескольких местах, а идентификаторы на странице должны быть уникальными. Поэтому используйте `useId`: сгенерированные идентификаторы не конфликтуют, даже если `PasswordField` показан несколько раз.

import { useId } from 'react';

function PasswordField() {
  const passwordHintId = useId();
  return (
    <>

        Пароль:
        <input

          aria-describedby={passwordHintId}
        />
      </label>
      <p id={passwordHintId}>
        Пароль должен содержать не менее 18 символов
      </p>
    </>
  );
}

export default function App() {
  return (
    <>
      <h2>Выберите пароль</h2>
      <PasswordField />
      <h2>Подтвердите пароль</h2>

    </>
  );
}

#### Чем `useId` лучше обычного инкрементируемого счётчика? {/*why-is-useid-better-than-an-incrementing-counter*/}

Глобальный счётчик (`nextId++`) ломается при [серверном рендеринге](/reference/react-dom/server). Сервер создаёт HTML, а клиент при [гидратации](/reference/react-dom/client/hydrateRoot) подключает к нему обработчики событий. Для этого клиентский вывод должен совпасть с HTML от сервера.

Со счётчиком совпадение почти не гарантировано: порядок гидратации клиентских компонентов может отличаться от порядка, в котором сервер составлял HTML. `useId` гарантирует, что идентификаторы на сервере и на клиенте совпадут.

Внутри React `useId` вычисляется на основе «пути из цепочки родителей» компонента, который его вызвал. Если деревья на сервере и на клиенте совпадают, то совпадают и эти пути, в каком бы порядке компоненты ни рендерились.

</DeepDive>
