1. Whole page: it isn't an ADR. It has no Status and date, no Decision paragraph ("We will …"), no Consequences and no Alternatives. It is a format spec (reference) with a short background section on top. A new maintainer looking for "why" finds only "Inspiration". Fix: split it in two. Put the field-by-field spec (Envelope, Metadata, Component) on a reference page and link to it. Keep an ADR that has Status with a date, Context, Decision ("We will describe entities in YAML files that live next to the code, in a Kubernetes-style envelope …"), Consequences and Alternatives. If the decision is already accepted and published, add the missing parts only if the original authors can supply them. Otherwise write a new ADR that supersedes this one, and add a one-line `superseded by` status here.
2. "Inspiration" and "Core Concepts": the page never says why the format is what it is. There is no reason for YAML, for one document per entity, for descriptor files in the team's own repo instead of only a central database, for the Kubernetes model, or for `apiVersion`/`kind`/`metadata`/`spec`. The Kubernetes link is a pointer, not a reason. Add an Alternatives list with one full sentence per option (for example JSON, a single central registry, a custom schema) saying why it was rejected. Add the reasons for each choice to Context.
3. "Inspiration", first paragraph: "a homegrown software catalog system is used heavily" and "certain pieces of metadata … are being carried over" are unverifiable and vague. Say which learnings and which metadata fields came from the Spotify catalog, or link to a source. Otherwise delete the paragraph. The words "heavy inspiration" appear twice (lines 26 and 21–24).
4. `apiVersion` and `kind` section: "The first versions of the catalog will focus on the `Component` kind" and "Early versions … will be using alpha/beta versions … After that, `backstage.io/v1`" go stale. A maintainer can't tell which state is current. Give the status and date at the top. Say what the alpha status means today, for example "as of `<DATE>` only `Component` is defined; the format is `v1alpha1`". Move the stability plan into Consequences.
5. Terms: one concept has several names. "Descriptor files", "entity definition" and "entity specification files" all mean the same thing. "Registry" (line 129) is undefined and appears to mean the catalog, and "software catalog" alternates with "the catalog". "Kubernetes" is lowercase in "kubernetes object format". Pick one term for each concept, define it at first use, and use it everywhere.
6. `labels` and `annotations`: the key-format paragraph (prefix, 253/63 limits, `backstage.io/` reserved) is copied word for word in both sections. Two copies will drift apart. State the rule once, as a shared "Key format" paragraph, and refer to it from both sections.
7. `namespace` and `name`: "unique per kind, within a given namespace (if specified)" doesn't say what applies when no namespace is given. Nothing says whether an entity without a namespace lands in a default one. "`v1` / `Namespace` entities" is unclear too. State the default namespace and the uniqueness scope, and write "entities of kind `Namespace` with `apiVersion: v1`, as in Kubernetes".
8. Format section, the paragraph after the example: it lists `name`, `namespace`, `labels` and `annotations` as the specially reserved fields but leaves out `description`. The example omits `namespace`. The text says the key `system` "has predefined semantics" and never says what they are, and `lifecycle` in the example has no explanation. Add `description` to the list, add `namespace` to the example or say why it is absent, and link to or state the meaning of `system` and `lifecycle`.
9. `description`: the example writes Markdown (a link) inside `description`, but the section says only "human readable". Say whether Markdown is rendered, or use plain text in the example.
10. Component section: `type` has only the example `service` and no list of allowed values or a link to one. Nothing says whether the value is free-form. Give the allowed values, or say that the field is free-form and where the values are defined. The front matter `description` ("Architecture Decision Record (ADR) log on …") repeats the title and describes a log rather than this decision. Replace it with one sentence stating the decision. Fix the grammar in "by push events from a CI/CD pipelines" (line 34). I didn't check the links to issue #390 and the Kubernetes pages.

Verdict: restructure first.
