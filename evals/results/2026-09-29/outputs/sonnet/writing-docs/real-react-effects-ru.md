Файл: `you-might-not-need-an-effect.md`, фрагмент до конца раздела про кеширование. Читатель: знает основы React и хочет понять, почему лишние эффекты вредят.

## Вывод

Мысль читается: сначала правило («эффект нужен для синхронизации с внешней средой»), затем два случая, затем примеры «плохо → хорошо». Этот порядок менять не надо.

Мешают читать три вещи:

- Причина вреда, то есть цепочка «рендер → фиксация → эффект → `setState` → рендер», размазана по длинным абзацам с ломаной грамматикой.
- Терминология плавает: `Эффект/эффект`, `кеш/кэш`, `рендер/рендеринг`, `затратный/дорогой/дорогостоящий`.
- В нескольких местах перевод сбивает смысл: «значительную сумму», «проверит если», «встроенно», «не помещайте это в состояние лучше».

## 1. Что мешает понять мысль

Порядок по важности.

**1.1. Механизм вреда спрятан в длинном пункте (строка 26).**
Это главный ответ на вопрос читателя, а он идёт одним абзацем в ~90 слов. В нём «Это не совсем эффективно» — расплывчато. «В начале ваших компонентов» вводит в заблуждение: код нужно писать на верхнем уровне компонента, а не «в начале».
Правка: заменить абзац пунктом и нумерованным списком.

> **Эффекты не нужны, чтобы преобразовывать данные для рендера.** Например, чтобы отфильтровать список перед показом. Это неэффективно. После каждого обновления состояния:
>
> 1. React вызывает компонент и вычисляет, что показать на экране (рендер).
> 2. React ["фиксирует"](/learn/render-and-commit) изменения в DOM (commit).
> 3. React запускает эффекты.
> 4. Если эффект вызывает `setState`, всё повторяется с шага 1.
>
> Чтобы не запускать лишние рендеры, преобразуйте данные на верхнем уровне компонента. Этот код сам выполнится снова при изменении пропсов или состояния.

**1.2. Второй пункт слабее сути (строка 27).**
Заголовок пункта «Эффекты для обработчиков событий» неясен. «Предпочтительно» смягчает: это вопрос корректности, а не вкуса.
Правка:

> **Эффекты не нужны, чтобы реагировать на действия пользователя.** Допустим, при нажатии «Купить» нужно отправить POST-запрос на `/api/buy` и показать уведомление. Обработчик клика знает, что именно сделал пользователь. К моменту запуска эффекта это уже неизвестно (например, какая кнопка была нажата). Поэтому обрабатывайте действия пользователя в обработчиках событий.

**1.3. Цепочка рендеров в первом примере описана нечитаемо (строка 51).**
«Выполняется полный цикл рендера со старым значением `fullName`, а затем же еще один с обновленным значением» — грамматически сломано. Читатель не видит, что «старое значение» — это пустая строка.
Правка:

> Этот код избыточен и неэффективен. Сначала компонент рендерится со старым `fullName` (при первом рендере это пустая строка). Затем эффект вызывает `setFullName`, и React рендерит компонент ещё раз, уже с новым значением.

**1.4. Ключевое правило и его обоснование склеены (строка 63).**
Фраза «не помещайте это в состояние лучше, вычислите» — склейка двух конструкций без знака. Три выигрыша спрятаны в предложении из 30+ слов с тремя скобками. «Каскадные» обновления упомянуты впервые и не связаны с цепочкой из 1.3.
Правка:

> **Если значение можно вычислить из текущих пропсов или состояния, не храните его в [состоянии](/learn/choosing-the-state-structure#avoid-redundant-state) — вычисляйте во время рендера.** Так код:
>
> * быстрее: нет лишних «каскадных» рендеров;
> * проще: меньше кода;
> * надёжнее: нет нескольких переменных состояния, которые могут разойтись друг с другом.
>
> Если подход кажется незнакомым, раздел [«Мышление в React»](/learn/thinking-in-react#step-3-find-the-minimal-but-complete-representation-of-ui-state) объясняет, что стоит хранить в состоянии.

**1.5. Причина, по которой нужен `useMemo`, не названа (строки 67, 94).**
`newTodo` появляется в коде на строке 70 без пояснения. На строке 94 он назван «несвязанной переменной», но не сказано, как он вызывает лишний пересчёт.
Правка для строки 94:

> Обычно такой код работает хорошо. Но `getFilteredTodos()` может быть медленной, а `todos` — много. Тогда лишний пересчёт при изменении несвязанной переменной, например `newTodo` (текст в поле ввода нового дела), даёт задержку: каждый введённый символ заново фильтрует весь список.

**1.5а. Механизм `useMemo` (строка 124) нельзя прочитать.**
«Проверит если», «не хотите чтобы … пока» — запятые и союзы потеряны, «внутренняя функция» неясна.
Правка:

> `useMemo` запоминает результат `getFilteredTodos()` при первом рендере. При следующем рендере React сравнивает `todos` и `filter` с прошлыми значениями. Если оба не изменились, `useMemo` возвращает сохранённый результат. Если изменились — вызывает функцию заново и сохраняет новый результат.

**1.6. Ограничение `useMemo` без причины (строка 126).**
«Это работает только для чистых вычислений» — читатель не понимает, что запрещено. К тому же точка попала внутрь ссылки, а перед «обёрнутые» нет запятой.
Правка:

> Функция внутри [`useMemo`](/reference/react/useMemo) выполняется во время рендера, поэтому она должна быть [чистой](/learn/keeping-components-pure): без запросов, изменения состояния и других побочных действий.

**1.7. Фраза про порог в DeepDive искажает смысл (строка 140).**
«Если общее указанное время в журнале, составляет значительную сумму (1 мс или больше)» — здесь «сумма» и лишняя запятая. «Журнал» — это консоль. «Оберните процесс» — не тот термин.

> Выполните действие, которое хотите измерить (например, введите текст в поле). В консоли появятся записи вроде `filter array: 0.15ms`. Если записи за одно действие в сумме дают 1 мс и больше, вычисление стоит кэшировать. Для проверки оберните его в `useMemo` и сравните суммарное время:

**1.8. Совет про строгий режим не связан с замером (строка 154).**
Читатель не понимает, при чём тут двойной рендер. «Так же учитывайте то, что» — «так же» надо писать «также», а «то, что» лишнее.
Правка:

> Также помните, что замеры в режиме разработки неточны: например, в [строгом режиме](/reference/react/StrictMode) компоненты рендерятся дважды. Для точных результатов соберите приложение в режиме продакшена и проверьте на устройстве, похожем на устройства ваших пользователей.

**1.9. Термины использованы до объяснения.**

| Термин | Где впервые | Правка |
|---|---|---|
| избыточное состояние | строка 42, комментарий в коде | Перед кодом, строка 35 или 51, добавить: «Такое состояние называют избыточным: его значение можно вычислить из других данных» |

**1.10. Введение обещает пользу, но не называет правило (строка 7).**
Правило заканчивается на строке 29, а вначале только «лазейка».
Правка:

> Эффекты — это выход за пределы React: с их помощью компонент синхронизируется с внешней средой — сторонним виджетом, сетью или DOM браузера. Если внешней среды нет (например, нужно обновить состояние при изменении пропсов), эффект не нужен. Без лишних эффектов код проще читать, он быстрее выполняется и реже ломается.

**1.11. Про загрузку данных сказано двусмысленно (строка 29).**
Сначала «можно запрашивать данные эффектами», потом «фреймворки лучше». Читатель не понимает, что делать.
Правка:

> Эффекты нужны для [синхронизации](/learn/synchronizing-with-effects#what-are-effects-and-how-are-they-different-from-events) с внешней средой. Например, эффект может синхронизировать виджет jQuery с состоянием React. Эффектами можно и загружать данные (синхронизировать результаты поиска с запросом), но встроенные механизмы [фреймворков](/learn/start-a-new-react-project#production-grade-react-frameworks) для этого эффективнее, чем эффекты, написанные прямо в компонентах.

## 3. Мелочи

- **Строка 7:** «Эффекты - это» → «Эффекты — это» (тире, не дефис). «за ее рамки» → «за её рамки» (в тексте уже есть «её» на строке 35, «ё» надо держать везде).
- **Строка 26:** «Например, для фильтра списка перед тем, как отобразить его» — фрагмент. Правка: «Например, чтобы отфильтровать список перед показом».
- **Строка 35:** двойной пробел в «мысль  добавить». **Строка 126:** двойной пробел в «для  [чистых».
- **Строка 94:** «Как правило, это хорошо работающий код!» → «Обычно такой код работает хорошо». Также «не пересчитывать … если» — запятая перед «если».
- **Строка 96:** «дорогое вычисление обернув его» → «затратное вычисление, обернув его» (запятая перед деепричастием).
- **Строка 132:** «Как правило … скорее всего» — двойное смягчение. «Для уверенности, добавьте запись в консоль для измерения» → «Чтобы убедиться, измерьте время с помощью `console.time`».
- **Строка 145:** пробел в конце строки в комментарии кода. Порядок «filter и todos» противоречит остальным «todos или filter».
- **Строка 150:** «спасёт от ненужных выполнений» → «избавит от лишних пересчётов при следующих рендерах».
- **Строка 152:** «встроенно» неверно. Правка: «Ваше устройство, скорее всего, быстрее, чем у пользователей, поэтому проверяйте производительность с искусственным замедлением. В Chrome для этого есть встроенное [замедление процессора](…)». Ссылка ведёт на запись о Chrome 61 (2017 год), вероятно устарела; заменить на актуальную страницу документации DevTools (не проверял).
- **«ваш» повторяется:** строки 7, 26, 63 («ваш код», «в ваших компонентах», «ваших компонентов»). Убрать притяжательное там, где смысл не меняется: «в компонентах», «код».
- **Восклицательные знаки:** строки 26 («начнётся заново!») и 31 («примеров!»). Это перенос тона оригинала. Если у проекта нет требования держать тон, убрать. Строка 31: «Чтобы развить интуицию, разберём несколько типичных примеров.»
- **Заголовок строки 33** («Обновление состояния на основе пропсов или состояния компонента») описывает тему, а не правило. Заголовок с правилом: «Производные значения: вычисляйте при рендере, а не в эффекте». Якорь `{/*updating-state-based-on-props-or-state*/}` оставить.
- **Строки 111–122:** второй блок с `useMemo` в одну строку дублирует предыдущий без нового смысла. Можно сократить до одной фразы: «Стрелочную функцию без `return` можно записать в одну строку: `useMemo(() => getFilteredTodos(todos, filter), [todos, filter])`». Если нужна поблочная параллель с оригиналом, оставить как есть.
