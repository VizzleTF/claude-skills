# Постмортем: деградация платёжного API Quenby, 2026-09-14

**Статус:** финальный
**Уровень серьёзности:** SEV-1 (существенное влияние на платежи, публичный сервис)
**Авторы:** дежурная смена SRE / команда платёжного API
**Аудитория:** все инженерные команды, руководство

---

## Краткое содержание

14 сентября 2026 года выкатка релиза v5.12.0 платёжного API привела к блокировке таблицы `payments` (48 млн строк) из-за миграции, создающей индекс без `CONCURRENTLY`. В течение ~29 минут доля ошибок 5xx достигала 62%. Инцидент устранён отменой миграции через `pg_cancel_backend`. Данные не потеряны; около 500 попыток оплаты не были повторены клиентами автоматически и потребовали ручной проверки.

## Влияние

- **Длительность деградации:** 09:44–10:13 UTC (~29 минут), из них ~62% ошибок 5xx на пике.
- **Неудачные попытки оплаты:** ~18 400.
- **Успешно повторены клиентами в течение часа:** ~17 900 (~97%).
- **Не повторены:** ~500 — требуют точечной проверки на предмет потерянной выручки/недовольства клиентов.
- **Потеря данных:** отсутствует.

**Наблюдение:** между откатом приложения (09:58) и фактическим устранением причины (10:11) прошло 13 минут — потому что откат кода не остановил уже запущенную миграцию. Это ключевой фактор, увеличивший длительность инцидента почти вдвое.

## Причина инцидента

**Непосредственная причина:** миграция в релизе v5.12.0 выполняла `CREATE INDEX` на таблице `payments` (48 млн строк) без модификатора `CONCURRENTLY`. Такая операция берёт блокировку, блокирующую чтение и запись в таблицу на всё время построения индекса, что на таблице такого размера вызвало массовые тайм-ауты и ошибки 5xx у клиентов платёжного API.

### Способствующие факторы

1. **Линтер миграций не проверяет `CREATE INDEX` без `CONCURRENTLY`.** Правило отсутствовало в наборе проверок, поэтому миграция прошла код-ревью и CI без предупреждений.
2. **Откат приложения не отменяет уже запущенную миграцию.** Процесс отката спроектирован для кода сервиса, но не имеет механизма остановки миграций БД, из-за чего блокировка продолжала действовать ещё 13 минут после отката.
3. **Staging не воспроизводит проблему из-за разницы в объёме данных.** В staging таблица `payments` содержит ~20 000 строк — построение индекса занимает доли секунды, и блокировка невидима при тестировании. На проде — 48 млн строк, тот же код ведёт себя принципиально иначе.

## Что сработало хорошо

- Алерт `PaymentsApiErrorRate` сработал быстро (через 3 минуты после начала деградации) и поднял дежурного.
- Данные не были потеряны: денежные операции остались консистентны.
- Подавляющее большинство клиентов (~97%) успешно повторили платёж без вмешательства.

## Что сработало плохо

- Первое действие по устранению (откат приложения) не устранило первопричину, что продлило инцидент.
- Дежурному потребовалось самостоятельно диагностировать, что причина — не в коде приложения, а в зависшей миграции БД, и вручную подобрать команду для её отмены — готового ранбука не было.
- Тестовый контур (staging) не мог заранее выявить проблему из-за нерепрезентативного объёма данных.

## Задачи по итогам (action items)

| Задача | Ответственный | Срок |
|---|---|---|
| Добавить в линтер миграций правило, запрещающее `CREATE INDEX` без `CONCURRENTLY` (или требующее явного исключения с обоснованием) | Команда платформы данных | 2026-10-15 |
| Составить ранбук по диагностике и отмене зависших/проблемных миграций (включая использование `pg_cancel_backend`/`pg_terminate_backend`, критерии принятия решения, эскалацию) | Дежурная смена SRE | 2026-10-01 |
| Обеспечить наполнение staging данными не менее 10% от объёма production для ключевых таблиц (включая `payments`) | Команда QA-инфраструктуры | 2026-11-30 |

## Извлечённые уроки

1. Откат приложения и остановка миграции БД — это два независимых действия; ни один процесс не должен считаться завершённым, пока не проверены оба.
2. Автоматические проверки (линтеры) должны ловить операционно опасные паттерны миграций до код-ревью, а не полагаться на внимательность ревьюера.
3. Репрезентативность staging по объёму данных — не техническая деталь, а необходимое условие для того, чтобы staging вообще мог поймать подобные проблемы.
