# Методичка для новых DevOps: платформа Pollard

## 1. Что нужно знать в первую очередь

Pollard — платформа, инфраструктура которой управляется по модели **GitOps**. Это значит:

- Единственный источник правды о состоянии кластеров — Git-репозиторий, а не то, что руками накатили в кластер.
- Синхронизацией репозитория и реального состояния кластера занимается **Argo CD**: он следит за манифестами и автоматически приводит кластер в соответствие с тем, что замержено в ветку.
- Твоя работа как DevOps — вносить изменения через Pull Request в нужный репозиторий, а не выполнять команды напрямую в кластере.

## 2. Репозитории

| Репозиторий | Что в нём | Когда используется |
|---|---|---|
| `infra-gitops` | Kubernetes-манифесты (Deployments, Services, ConfigMaps, Helm-values и т.д.), которые читает Argo CD | Любое изменение состояния приложений/сервисов в кластерах |
| `infra-terraform` | Terraform-код для облачной инфраструктуры (сети, кластеры, базы данных, IAM и т.п.) | Изменения инфраструктуры уровня "ниже кластера" — то, что не описывается k8s-манифестами |

**Правило:** если можно решить задачу через `infra-gitops` — делаем через `infra-gitops`. К `infra-terraform` обращаемся только для инфраструктурных изменений, которые не покрываются k8s-манифестами.

## 3. Кластеры

Есть два окружения:

- **stage** — тестовый кластер, куда выкатываются изменения перед прод. Ошибки здесь не критичны — для этого он и существует.
- **prod** — боевой кластер. Любая ошибка здесь напрямую влияет на пользователей.

Оба кластера подключены к Argo CD и синхронизируются из `infra-gitops` (обычно из разных веток или директорий/overlay — уточни у наставника точную структуру путей в репозитории, если не очевидно из `Application`-манифестов Argo CD).

## 4. Как получить доступ

Доступы **не выдаются автоматически** и не запрашиваются в личных сообщениях. Процесс такой:

1. Завести заявку в очередь **OPS** — с указанием, какой доступ нужен (например: доступ на чтение/запись в `infra-gitops`, доступ к Argo CD UI, доступ к kubeconfig stage/prod и т.д.) и зачем.
2. Дождаться обработки заявки.
3. Проверить, что доступ реально работает, **до** того, как он понадобится в боевой задаче.

Если не уверен, какой конкретно доступ нужен для задачи — сначала спроси у наставника или в командном чате, потом заводи заявку. Так меньше шансов запросить не то или пойти по кругу.

## 5. Главное правило: как мы не трогаем prod

**В prod ничего не применяется руками.**

Это значит:

- ❌ Никаких `kubectl apply`, `kubectl edit`, `kubectl scale`, `kubectl delete` и т.п. напрямую в prod-кластере, даже "временно" и даже "просто посмотреть, поможет ли".
- ❌ Никаких ручных правок через Argo CD UI, которые расходятся с тем, что лежит в Git (Argo CD такие изменения потом просто откатит — и это ожидаемо правильное поведение).
- ✅ Единственный способ изменить prod — смёрджить изменение в `infra-gitops`, после чего Argo CD применит его сам.

**Почему это важно:** если менять кластер руками, Git перестаёт быть источником правды. Реальное состояние кластера расходится с репозиторием, Argo CD начинает "воевать" с ручными правками (откатывать их), а следующий человек, который будет разбираться в инциденте, не сможет понять по Git, что реально происходит в проде. GitOps-подход существует именно для того, чтобы у любого изменения в проде была история, автор и код-ревью.

Если нужно сделать что-то экстренно (инцидент, прод лежит) — это отдельная процедура эскалации, не описанная в этой методичке; уточни её на дежурстве или у тимлида **до** того, как она понадобится.

## 6. Процесс Pull Request

Любое изменение в `infra-gitops` (и в `infra-terraform`) проходит через PR:

1. Создаёшь ветку, вносишь изменения в манифесты.
2. Открываешь Pull Request с понятным описанием: что меняется и зачем.
3. **PR должен получить два (2) одобрения** прежде чем его можно смёржить. Одобрение одного ревьюера — недостаточно, даже если "и так всё понятно".
4. После мержа Argo CD подхватывает изменения автоматически — руками синхронизацию форсировать не нужно (но можно проверить статус синка в Argo CD UI).

Не пытайся смёржить PR с одним апрувом "для скорости" — правило двух одобрений действует одинаково и для stage, и для prod.

## 7. Твоя первая задача

Первая задача для любого нового DevOps на платформе Pollard — **выкатить изменение в stage через `infra-gitops`**. Смысл задачи не в сложности самого изменения, а в том, чтобы пройти весь GitOps-цикл руками:

1. Получить доступ к `infra-gitops` через заявку в OPS (см. раздел 4), если ещё не получен.
2. Найти в репозитории манифесты, относящиеся к stage-окружению.
3. Внести небольшое изменение (обычно наставник подскажет конкретную задачу — например, поменять значение в ConfigMap, обновить тег образа и т.п.).
4. Открыть PR, дождаться двух одобрений.
5. Смёржить и убедиться в Argo CD UI, что Application синхронизировался и стал `Healthy`/`Synced`.
6. Проверить результат непосредственно в stage-кластере (что изменение реально применилось).

Это упражнение — база для всего остального: тот же цикл (ветка → PR → 2 апрува → мерж → Argo CD применяет) используется и для прода, только с большей осторожностью и обычно более тщательным тестированием на stage перед этим.

## 8. Дежурства

- На дежурство новичок выходит **через 4 недели** после начала работы.
- До этого момента ты не несёшь дежурную нагрузку, но стоит уже сейчас изучать, как устроен мониторинг, алерты и процедура эскалации — это сильно облегчит первые дежурства.

## 9. Краткий чек-лист на первые недели

- [ ] Завести заявку в OPS на доступы (`infra-gitops`, Argo CD, kubeconfig для stage)
- [ ] Изучить структуру репозитория `infra-gitops` (где stage, где prod, где общие компоненты)
- [ ] Посмотреть Argo CD UI: какие `Application` есть, как выглядит `Synced`/`OutOfSync`/`Healthy`/`Degraded`
- [ ] Выполнить первую задачу — выкатить изменение в stage
- [ ] Изучить структуру `infra-terraform` (для будущих инфраструктурных задач)
- [ ] Понять процедуру эскалации/инцидентов до выхода на дежурство (через 4 недели)

## 10. Ключевые правила одним списком (памятка)

1. Источник правды — Git, а не кластер.
2. В prod — никакого `kubectl apply` руками, только merge в `infra-gitops`.
3. Любой PR требует два одобрения.
4. Доступы — только через заявку в очередь OPS.
5. Terraform (`infra-terraform`) — для инфраструктуры, k8s-манифесты (`infra-gitops`) — для всего остального.
6. Сначала stage, потом prod.
