Бриф для `/autopilot`. Собран 2026-09-28 из диалога с владельцем репозитория: разбор
текущего скилла `writing-docs`, исследование практик технического письма, интервью.

## Цель

Собрать новый скилл для Claude Code, который пишет и ревьюит документацию **по типу
документа**, и сравнить его с текущим скиллом `writing-docs` на наборе сценариев.
По итогам сравнения владелец решает, какой скилл лучше и почему.

Результат должен быть доведён до эталона, а не до «рабочего черновика».

## Классификация документов

Слова «инструкция», «описание», «методичка» называют форму, а не задачу читателя.
«Описание» скрывает справочник или объяснение. «Методичка» — обучение, сборник
рецептов или нормативные правила команды. Скилл выбирает тип по читателю и его
состоянию, а не по названию, которое дал пользователь.

Оси: две оси Diátaxis (действие/понимание, учёба/работа), плюс жизненный цикл
(живой документ или запись момента), плюс место (отдельная страница или код/интерфейс).

### Живые документы — правятся вместе с продуктом

| Тип | Читатель и момент | Каркас |
|---|---|---|
| Tutorial | новичок, учится | цель и время → шаги с ожидаемым выводом → видимый результат → «что дальше» |
| How-to | знает тему, посреди работы | заголовок-задача → предпосылки → шаги → проверка → «если не сработало» |
| Runbook | дежурный, стресс, ночь | имя алерта → влияние и срочность → диагностика → действие → проверка → откат → эскалация |
| Troubleshooting | упёрся в ошибку | таблица: сообщение дословно → причина → действие |
| Reference | ищет один факт | однородные записи: имя → тип → по умолчанию → пределы → пример |
| Explanation | хочет понять, не работает прямо сейчас | связная проза: контекст → устройство → альтернативы → следствия |
| README | пришёл впервые | один экран: что это → кому → установка → минимальный пример → ссылки |
| Conventions | член команды | правило → зачем → пример «плохо → хорошо»; модальность MUST/SHOULD/MAY |

### Записи — фиксируют момент, не правятся, а замещаются

| Тип | Каркас |
|---|---|
| Design doc / RFC → ADR | контекст → решение → последствия (все, не только плюсы) → альтернативы; статус, дата, `supersedes` |
| Postmortem | влияние → хронология в UTC → причины → задачи с владельцем и сроком; без поиска виноватых |
| Changelog / release notes / миграция | версия и ISO-дата → Added/Changed/Deprecated/Removed/Fixed/Security; ломающие изменения первыми |

### В коде и интерфейсе

| Тип | Правило-якорь |
|---|---|
| Docstring / комментарий | только то, чего не видно из кода: единицы, границы, инварианты, «почему»; не пересказывать сигнатуру |
| `--help` / сообщение об ошибке | что сломалось → какой ввод неверен → как исправить → пример |

## Правила по типам: голос и глаголы

| Тип | Лицо и наклонение | Особое |
|---|---|---|
| Tutorial | «мы» плюс повелительное в шагах (Diátaxis) | объяснения минимальны и со ссылкой, не ноль; один путь без ветвлений |
| How-to | повелительное, заголовок инфинитивом («Добавить пакет») | условие раньше действия; одно действие на шаг; результат в настоящем времени |
| Runbook | повелительное, без прозы | команды копируются целиком, плейсхолдеры явные (`<NAMESPACE>`); проверка и откат у каждого действия; дата последней проверки |
| Reference | изъявительное, третье лицо («Задаёт таймаут») | только факты, без советов |
| Explanation | изъявительное, «мы» допустимо | «известное → новое»; шагов нет |
| Conventions | модальность по шкале обязательно / рекомендуется / можно | правило без «зачем» не принимается |
| ADR | решение в действительном залоге: «Мы используем X» (Nygard) | полные предложения, не обрывки в списках; 1–2 страницы |
| Postmortem | прошедшее время | системные причины, не люди (Google SRE) |
| Changelog | для людей, не выгрузка `git log` (Keep a Changelog) | новое сверху |
| Docstring (Python) | первая строка повелительная: «Return X» (PEP 257) | в других языках — конвенция проекта |

### Где общие правила ломаются

Эти исключения скилл должен знать явно. В `writing-docs` их нет, из-за этого он даёт
неверные советы для части типов.

| Общее правило | Где ложно | Что вместо него |
|---|---|---|
| Неправдивую страницу удалить | ADR, postmortem, changelog | не править; пометить `superseded`, дать ссылку на новую запись |
| Больше двух частей — список | ADR, explanation | полные предложения |
| Второе лицо | tutorial, reference, postmortem | «мы» / третье лицо / прошедшее время |
| Ответ первым | tutorial | первой строкой цель: «В конце у вас будет X» |
| Ни один факт не дублировать | README, tutorial, runbook | runbook держит команды у себя; контекст и предпосылки повторять можно, нормативные факты — нет |

## Архитектура скилла

Один скилл с маршрутизатором по типам (паттерн Anthropic «domain-specific
organization»), а не 12 отдельных скиллов: иначе ядро правил дублируется, бюджет
описаний раздувается, скиллы спорят за срабатывание.

- `SKILL.md` — маршрутизатор, ядро правил, общий workflow с копируемым чек-листом,
  ветки «создать / ревью / набор документов». Цель — около 150 строк, чтобы он
  целиком переживал автокомпакцию.
- Файл на каждый тип. Одинаковые разделы во всех: «Когда это он и когда нет»,
  «Каркас», «Голос и глаголы», «Объём», «Отличия от общих правил», «Запрещено»,
  «Чек-лист типа».
- Файлы стиля: английский, русский, LLM-паттерны.
- Процесс: план набора документов (аудитория, инвентаризация, приоритет,
  friction log) и ревью чужого текста.
- Скрипт детерминированных проверок: длинные предложения, стоп-слова, LLM-маркеры,
  битые ссылки. Если в системе есть Vale — использовать его.
- Источники.

### Требования Anthropic и Claude Code

- Ссылки только на один уровень от `SKILL.md`: файл типа не отправляет к файлу стиля,
  связку «тип + стиль» задаёт `SKILL.md`.
- Файлы длиннее 100 строк начинаются с оглавления.
- `description` пишется от третьего лица и говорит, что делает скилл. Триггеры на
  русском и английском идут в `when_to_use`. Вместе не больше 1536 символов.
- Пути к скриптам через `${CLAUDE_SKILL_DIR}`.
- Один термин на одно понятие во всём скилле.
- Нет информации, которая протухнет по дате.
- Тексты самих скиллов соблюдают свои правила: без афоризмов, отрицательных
  параллелизмов («не X, а Y»), правила трёх, частых тире, нагнетания.
- `claude plugin validate .` проходит без ошибок.

Источники требований:
- <https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices>
- <https://code.claude.com/docs/en/skills>
- <https://code.claude.com/docs/en/plugin-marketplaces>

### Две языковые версии

`technical-writing` и `technical-writing-ru` равны по содержанию и структуре.
Отличаются только языком инструкций. Русская версия — не дословный перевод: она
написана по-русски и соблюдает русские правила стиля. Проверка паритета входит
в приёмку.

## Что новый скилл обязан исправить по сравнению с writing-docs

Разбор `~/.claude/skills/writing-docs` выявил:

1. ARID из Write the Docs приписан наоборот («отсутствие дублей»). На деле ARID —
   *Accept (some) Repetition In Documentation*.
2. Противоречие «страница самодостаточна» против «ни одного дубля».
3. Статистика NN/g 1997 года (79/16, +124%) подана главным аргументом, хотя
   исследование было на промо-сайте, а не на технической документации.
4. Жёсткие пороги без источника: «не длиннее 25 слов», «сократи вдвое». Второе —
   третий закон Круга про веб-страницы, применённый ко всему. Нужны ориентиры, не законы.
5. Нет Williams, Pinker, Zinsser, Strunk & White, Minto, Redish, IBM DQTI,
   *Docs for Developers*, Норы Галь, Чуковского.
6. Скилл нарушает собственные запреты: «Заголовок — карта, а не шутка» и подобные
   фразы, частые тире.
7. Нет этапа «до первой страницы»: аудитория, план, приоритет, проверка на читателе.
8. Нет раздела LLM-паттернов.
9. Глаголам отведена одна строка.
10. Нет связности текста: «известное → новое», тема абзаца.
11. Проклятие знания описано одной фразой, в чек-листе нет проверки живым читателем.
12. Нет runbook, postmortem, design doc, conventions, docstrings — хотя docstrings
    заявлены в description.
13. Нет русской типографики: ё, «ёлочки», тире и дефис, неразрывный пробел.
14. Визуальное содержимое сведено к «скриншоты резать».
15. Машинные проверки на grep ловят только однострочные предложения.
16. Diátaxis применён слишком жёстко: «ноль объяснений» в tutorial.

## Сравнение A/B

### Участники прогона

1. `writing-docs` из `~/.claude/skills/writing-docs` — базовая версия.
2. `technical-writing`.
3. `technical-writing-ru`.
4. Без скилла — контроль, чтобы видеть, помогает ли скилл вообще.

### Изоляция

Каждый прогон видит ровно один скилл о документации. У владельца глобально
включены хуки и режимы, меняющие стиль ответа (caveman, ponytail), и есть скилл
`humanizer`. Они загрязнят выходы. Прогоны должны идти без пользовательских хуков,
глобального `CLAUDE.md` и посторонних скиллов.

### Сценарии

Минимум один на каждый тип из классификации, плюс:

- неоднозначные запросы: «напиши описание сервиса», «сделай методичку для новых
  девопсов», «нужна инструкция по деплою»;
- ревью существующего текста;
- правка записи: «обнови ADR-0007, решение поменялось» — ожидается новая запись
  со `supersedes`;
- сценарии на русском и на английском.

Реальные документы — только из публичных репозиториев (см. открытые вопросы).

### Оценка

- Судья-модель получает сценарий и выход без имени скилла, порядок перемешан.
- Рубрика: верно выбран тип; каркас типа соблюдён; фактическая точность; ответ
  первым; сканируемость; голос и глаголы по типу; отсутствие LLM-паттернов; объём
  без воды; пригодность к действию.
- Сводная таблица по сценариям и критериям, разбор пар, где скиллы расходятся сильнее
  всего.
- Финальный вердикт выносит владелец по подготовленным парам.
- Раннер воспроизводим одной командой, результаты коммитятся в `evals/results/<дата>/`.

## Критерии приёмки

1. Оба скилла устанавливаются через `/plugin marketplace add VizzleTF/claude-skills`
   и `/plugin install <имя>@vizzletf-skills`.
2. `claude plugin validate .` проходит без ошибок.
3. Каждый из 16 пунктов «Что новый скилл обязан исправить» закрыт; видно, где именно.
4. Все типы из классификации покрыты файлами с одинаковой схемой разделов.
5. Паритет версий: у каждого файла английской версии есть русский аналог с тем же
   набором правил.
6. Тексты скиллов проходят собственный скрипт проверок и собственный чек-лист.
7. A/B-прогон выполнен по всем сценариям и всем четырём участникам, отчёт готов
   к вердикту владельца.
8. `README.md` репозитория: что это, как установить, как запустить сравнение.

## Ограничения

- Не изменять `~/.claude/skills/writing-docs` и ничего не ставить в `~/.claude/skills`.
- Репозиторий публичный: никаких приватных данных, внутренних имён хостов, секретов.
- Коммиты — Conventional Commits на английском, без `Co-Authored-By` и любых
  упоминаний ИИ.
- Push и публикация наружу — только с подтверждения владельца.

## Открытые вопросы

1. Какие именно публичные репозитории или документы взять как реальные сценарии.
   Владелец выбрал «только публичные», конкретные ещё не названы.
2. Содержат ли обе версии правила стиля для **обоих** языков документов.
   Предположение: да, потому что язык инструкций скилла не равен языку документа,
   который пишет пользователь. Подтвердить.
3. На каких моделях гонять сравнение и в каком бюджете. Anthropic советует
   проверять скиллы на Haiku, Sonnet и Opus.
