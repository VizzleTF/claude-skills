# Спецификация: скиллы technical-writing и technical-writing-ru

## Задача

Владелец пишет документацию с Claude Code и пользуется скиллом `writing-docs`. Скилл один на все документы. Поэтому он даёт неверные советы для части типов: велит удалять устаревший ADR, требует второго лица в справочнике, запрещает объяснения в tutorial. Разбор выявил 16 конкретных дефектов. Владельцу нужен скилл, который выбирает правила по типу документа. Кроме того, нужно доказательство, что новый скилл лучше старого. Мнения автора для этого мало.

## Решение

Появляется публичный маркетплейс `vizzletf-skills` с двумя плагинами, `technical-writing` и `technical-writing-ru`. Скилл определяет тип документа по читателю, загружает файл этого типа и файл стиля и ведёт работу по копируемому чек-листу. Скрипт проверок ловит длинные предложения, стоп-слова, LLM-маркеры, битые ссылки и нарушения типографики. В `evals/` лежат сценарии, рубрика и раннер. Одна команда прогоняет четырёх участников на выбранных моделях. Судья-модель оценивает выходы вслепую, а отчёт готовит пары для вердикта владельца.

## Пользовательские истории

Кто: **автор** — человек, который просит Claude написать или отревьюить документ; **владелец** — хозяин репозитория, он запускает сравнение и выносит вердикт; **посетитель** — сторонний пользователь маркетплейса.

## Решения по реализации

### §1. Стек и размещение

- Скрипты на Python 3 без зависимостей: `check.py`, `parity.py`, раннер. Почему: Python есть у Claude Code почти везде, а без зависимостей скрипт скилла запускается сразу после установки.
- Тесты на `unittest` из стандартной библиотеки; команда `python3 -m unittest discover -s tests`. Почему: никакой установки.
- Сценарии — Markdown-файлы с заголовком `ключ: значение` до первой пустой строки. Почему: промпты пишутся удобно, парсер на 15 строк.
- Результаты — Markdown и JSON.

### §2. Состав скилла (одинаковый в обеих версиях)

```
skills/technical-writing[-ru]/
├── SKILL.md
├── types/  tutorial.md how-to.md runbook.md troubleshooting.md reference.md
│           explanation.md readme.md conventions.md adr.md postmortem.md
│           changelog.md docstring.md cli-help-errors.md
├── style/  english.md (EN) | russian.md (RU), llm-patterns.md
├── process/ doc-set.md review.md
├── scripts/ check.py
└── sources.md
```

Имена файлов в обеих версиях английские и одинаковые. Почему: паритет проверяется по путям. Язык версии задают тексты, а не имена.

Разделы файла типа, в этом порядке. EN: `When to use it and when not`, `Skeleton`, `Voice and verbs`, `Length`, `Differences from the core rules`, `Forbidden`, `Type checklist`. RU: «Когда это он и когда нет», «Каркас», «Голос и глаголы», «Объём», «Отличия от общих правил», «Запрещено», «Чек-лист типа».

Голос для типов, которых нет в таблице брифа, решён по их каркасам. README: изъявительное в описании и повелительное в установке. Troubleshooting: изъявительное в причине и повелительное в действии. `--help` и сообщение об ошибке: изъявительное в «что сломалось» и повелительное в «как исправить».

«Объём» в каждом типе — ориентир с источником или с пометкой «эмпирика». Жёстких порогов нет (дефект 4).

SKILL.md содержит: frontmatter; назначение в двух строках; глоссарий терминов скилла; оси и таблицу выбора типа; таблицу «слово запроса → тип»; маршрут «тип → файл»; ветки «создать / ревью / набор документов»; ядро правил: читатель, ответ первым (кроме исключений типа), один термин — одно понятие, связность «известное → новое» и тема абзаца в первом предложении, примеры запускаются, актуальность, повтор допустим (ARID); правило о визуальном содержимом (дефект 14): картинка только там, где текст хуже — архитектура, поток, интерфейс; диаграмма как код (Mermaid и подобные), чтобы её правили вместе с текстом; у скриншота обрезка до нужной области, выделение действия, alt-текст и текстовый эквивалент шага; таблица вместо картинки для данных; подпись говорит, что читатель должен увидеть; копируемый чек-лист workflow; вызов скрипта; проверку живым читателем (субагент с холодным контекстом или человек); ссылку на `sources.md`.

Workflow (в чек-листе):
1. Читатель, его задача и состояние.
2. Тип, загрузить файл типа, файл стиля и LLM-паттерны.
3. Каркас.
4. Черновик.
5. Правка в несколько проходов: структура, абзацы и связность, предложения, слова; второй черновик — первый минус около 10% (King), это ориентир.
6. `check.py`.
7. Чек-лист типа.
8. Проверка холодным читателем.

### §3. `check.py`

Правила. `rule-id` стабильны, и отчёт их называет.

| rule-id | Уровень | Что |
|---|---|---|
| `sentence-length` | warning | предложение длиннее `--max-words` (по умолчанию 30 EN и 25 RU); предложения собираются через переносы строк |
| `stop-word` | warning | слово из списка стоп-слов языка (EN: just, simply, obviously, basically, very, really, easy…; RU: по категориям Ильяхова — усилители, оценки, канцелярит, вводные) |
| `llm-marker` | warning | слово или оборот из каталога LLM-маркеров (EN: delve, leverage, seamless, robust, "it's worth noting", "not just X but Y"; RU: «является», «играет ключевую роль», «стоит отметить», «не просто X, а Y») |
| `dash-density` | warning | больше 1 длинного тире на 40 слов в абзаце |
| `broken-link` | error | относительная ссылка на несуществующий файл или якорь |
| `dated-phrase` | warning | год 20xx и слова «сейчас / currently / as of» в прозе |
| `ru-quotes` | error | прямые кавычки `"` в русской прозе |
| `ru-dash` | error | ` - ` вместо ` — ` между словами |
| `ru-yo` | warning | «е» в словах из короткого списка, где «ё» различает смысл (всё/все, ещё и т. п.) |
| `ru-nbsp` | warning | обычный пробел перед « — » в русской прозе (нужен неразрывный) |
| `vale` | как у Vale | при наличии Vale и `.vale.ini` |

Не проза: fenced и inline code, таблицы (проверяются только слова), frontmatter, URL, HTML-комментарии. Язык: `--lang en|ru|auto`, `auto` — по доле кириллицы в прозе. Ссылки наружу по умолчанию не проверяются, флаг `--check-urls` проверяет их через `urllib`.

Вывод: `путь:строка: уровень rule-id: сообщение`, в конце сводка. `--format json` для машинной обработки. Код выхода: 0 — нет `error`; 1 — есть `error`; 2 — ошибка запуска. Сообщения на английском в обеих версиях: скрипт — код, не текст скилла.

Скрипт одинаковый в обеих версиях и содержит списки для обоих языков. Это не противоречит ответу «каждая только свой язык»: ответ касается правил стиля в тексте скилла, а скрипт — это инструмент. Тест проверяет, что два файла побайтово равны.

### §4. Паритет

`tools/parity.py` сравнивает `plugins/technical-writing/skills/technical-writing` и `plugins/technical-writing-ru/skills/technical-writing-ru`:
- одинаковый набор путей, кроме `style/english.md` ↔ `style/russian.md`;
- по каждой паре: одинаковое число заголовков каждого уровня, пунктов `- [ ]` и строк таблиц;
- `scripts/check.py` побайтово равен.

Он же проверяет структурные требования: семь разделов типа по порядку, оглавление в файлах длиннее 100 строк, SKILL.md ≤ 170 строк, `description + when_to_use` ≤ 1536 символов, отсутствие ссылок из `types/`, `style/`, `process/` на другие файлы скилла. Смысловой паритет проверяет ревью (Phase 6) и доводка.

### §5. Раннер `evals/run.py`

```
python3 evals/run.py [--models sonnet] [--core-models haiku,opus] [--judge-model opus]
                     [--participants writing-docs,technical-writing,technical-writing-ru,none]
                     [--scenarios GLOB] [--jobs 3] [--date YYYY-MM-DD] [--baseline-path PATH]
                     [--dry-run] [--skip-judge] [--report-only] [--reveal]
```

Генерация. Для каждой тройки «модель × участник × сценарий»:
1. Временный рабочий каталог с фикстурами сценария.
2. Временный `CLAUDE_CONFIG_DIR` со ссылкой на `~/.claude/.credentials.json`. Для `writing-docs` в нём ещё ссылка `skills/writing-docs`.
3. Вызов `claude -p --model M --no-session-persistence --output-format stream-json --verbose --permission-mode acceptEdits --plugin-dir <plugin>` (у `none` и `writing-docs` без `--plugin-dir`), промпт — текст сценария плюс фиксированная приписка: «верни итоговый документ целиком в последнем сообщении».
4. Из `stream-json` берутся итоговый текст, факт вызова Skill и его имя, стоимость и длительность.

Выход записывается в `outputs/<модель>/<участник>/<сценарий>.md`, метаданные — в `.json` рядом.

Оценка. На каждую пару «модель × сценарий» — два вызова судьи (`claude -p --model opus --json-schema <схема>` в пустом изолированном конфиге без плагинов). Судья получает сценарий, список фактов, рубрику и выходы под метками A–D в двух перестановках, заданных seed от имени сценария. Перед показом из выходов вырезаются упоминания имён скиллов. Результат — `judgments/<модель>/<сценарий>.json`.

Отчёт `report.md`:
- параметры прогона;
- сводная таблица «участник × критерий» (среднее) по основной модели;
- таблица «сценарий × критерий» для каждого участника (по основной модели);
- та же таблица по Haiku и Opus на ключевых сценариях;
- таблица по сценариям: итог каждого участника, слов, «скилл сработал»;
- позиционные расхождения;
- упавшие вызовы;
- ссылка на `pairs/` и `verdict.md` для слепого вердикта владельца (истории 64a–64d); до `--reveal` отчёт не называет, какая метка у какого участника.

Все внешние вызовы проходят через одну функцию `call_claude(argv, cwd, env) -> CallResult`. Тесты подменяют её.

### §6. Сценарии

Формат `evals/scenarios/<id>.md`:
```
id: runbook-disk-full
lang: en
kind: create | review | update | ambiguous
expect: runbook            # один тип или несколько через запятую
core: true|false
fixtures: runbook-disk-full/   # необязательно, каталог в evals/fixtures/
facts:
- The alert is NodeDiskUsageHigh, fires at 85%
- ...

<текст запроса автора>
```

Набор: 13 типов (минимум по одному), 3 неоднозначных (RU), 2 ревью (EN и RU), 1 `adr-supersede`, 8–10 на реальных документах из публичных репозиториев (ревью или переработка). Итого 27–30, из них ~8 `core`, покрывающих разные типы, оба языка и все виды `kind`. Реальные документы: лицензия допускает распространение (Apache-2.0, MIT, CC BY), в `evals/fixtures/SOURCES.md` для каждого указаны URL, коммит и лицензия. Синтетические продукты вымышлены и не совпадают с реальными именами.

### §7. Рубрика

`evals/rubric.md`: 9 критериев брифа, у каждого якоря на 1, 3 и 5 баллов. Отдельные правила для судьи: длина не заслуга; ответ на неоднозначный запрос с верным уточнением засчитывается как верный выбор типа; стиль оценивается по языку документа.

### §8. Прочее

- `docs/writing-docs-fixes.md` — 16 дефектов → где закрыты.
- README репозитория: что это, выбор версии, установка, запуск проверок, запуск сравнения, ссылка на последний отчёт.
- `plugin.json` обеих версий: `version` 0.1.0.
- Секреты: раннер никогда не читает содержимое `.credentials.json`, а только ставит на него ссылку.
- Коммиты — Conventional Commits на английском, без `Co-Authored-By` и упоминаний ИИ (R61; правило владельца главнее служебной подписи).
