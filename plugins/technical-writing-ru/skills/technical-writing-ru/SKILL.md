# Техническое письмо

## Содержание

Глоссарий, Выбор типа, Маршрут, Ветки, Общие правила, Порядок работы, Источники.

Скилл пишет документацию по типам и проводит её ревью. Сначала он определяет читателя, потом выбирает один из 13 типов документа и загружает правила этого типа.

## Глоссарий

- **Читатель**: человек, для которого написан документ. У него есть задача и состояние: учится, работает, действует в стрессе, ищет один факт.
- **Тип**: один из 13 типов документа из таблицы маршрута. Типы названы так же, как их файлы.
- **Файл типа**: файл в `types/` с правилами одного типа.
- **Каркас**: разделы, которые тип требует, в заданном порядке.
- **Общие правила**: правила из этого файла. Они действуют для любого типа, пока файл типа не скажет иначе.
- **Живой документ**: страница, которая меняется вместе с продуктом. Когда она перестаёт быть верной, её исправляют или удаляют.
- **Запись**: страница, которая фиксирует момент. Её содержание не правят. Кроме опечаток и битых ссылок, в опубликованную запись вносят только отметку о статусе (`[YANKED]`, `superseded by`) и ссылку на замену.
- **Замещена**: статус записи, которую заменила более новая. Старая запись получает этот статус и ссылку на новую.
- **Замечание**: одна проблема, найденная при ревью. Его формулируют как «где, что, как исправить».
- **Холодный читатель**: тот, кто не видел ни черновика, ни его контекста: свежий субагент или человек.

## Выбор типа

Слово из запроса («описание», «гайд», «методичка») называет форму. Тип определяет читатель. Определите, где запрос находится на каждой из четырёх осей:

| Ось | Один полюс | Другой полюс |
|---|---|---|
| Цель | читатель действует | читатель хочет понять |
| Ситуация | читатель учится | читатель работает |
| Жизненный цикл | живой документ | запись |
| Место | отдельная страница | код или интерфейс |

| Читатель и его момент | Тип |
|---|---|
| Новичок учится на практике и идёт по одному проложенному пути | tutorial |
| Знает тему, занят задачей, ему нужны шаги к одной цели | how-to |
| Дежурит, сработал алерт, времени мало | runbook |
| Получил конкретное сообщение об ошибке или видит симптом | troubleshooting |
| Ищет один факт: параметр, поле, лимит | reference |
| Хочет понять, почему система устроена именно так | explanation |
| Впервые пришёл в проект | README |
| Участник команды, который обязан следовать общим договорённостям | conventions |
| Ищет запись о решении и его компромиссах | ADR (включая design doc и RFC) |
| Ищет запись об инциденте и о том, что сделали после | postmortem |
| Обновляется и хочет знать, что изменилось | changelog (включая release notes и руководство по миграции) |
| Читает или вызывает код | docstring или комментарий в коде |
| Запускает команду или получил ошибку в инструменте | справка CLI или сообщение об ошибке |

### Слова запроса

| Слово запроса | Вопросы о читателе | Возможные типы |
|---|---|---|
| «описание», description | Читателю нужен факт, причины устройства системы или первое знакомство с проектом? | reference, explanation, README |
| «гайд», «методичка», «руководство», guide, manual | Читатель учится, решает одну рабочую задачу или следует правилам команды? | tutorial, how-to, conventions |
| «инструкция», instructions | Читатель выполняет плановую задачу или реагирует на алерт или ошибку? | how-to, runbook, troubleshooting |
| «документация», «доки», docs | Нужна одна страница или набор? Кто прочтёт первым? | ветка «Набор документов» |
| «заметки», «записка», notes, write-up | Это запись о решении, инциденте или релизе? | ADR, postmortem, changelog |

Если запрос не определяет тип, задайте один вопрос о читателе и предложите ответ по умолчанию. Пример: «Кто это прочтёт: новый инженер, который изучает деплой, или тот, кто деплоит сегодня? Если не скажете, напишу how-to для второго». Если ответить некому, одной строкой назовите допущение и продолжайте.

У одного документа один тип. Если запросу нужны два типа, предложите два документа и перейдите в ветку «Набор документов».

## Ветки

**Создать.** Идите по чек-листу из раздела «Порядок работы» с первого шага.

**Ревью.** Определите тип готового текста, загрузите его файл типа, файл стиля и каталог паттернов и следуйте [process/review.md](process/review.md). Выдайте замечания; переписывайте текст, только если об этом попросили. Запись при ревью остаётся как есть: предложите новую запись, которая её заместит.

**Набор документов.** Для запроса «задокументируй проект», для запроса, которому нужны несколько типов, и для аудита документации следуйте [process/doc-set.md](process/doc-set.md). Потом пройдите ветку «Создать» для каждой страницы в порядке приоритета.

## Общие правила

**Читатель.** Запишите одним предложением, кто читает страницу, что он пытается сделать и в каком он состоянии. Все дальнейшие решения выводятся из этого предложения.

**Ответ первым.** Вывод идёт раньше рассуждения: на странице, в разделе, в абзаце и в пункте списка. Tutorial вместо вывода начинается с цели. Другие исключения перечислены в файлах типов.

**Самодостаточная страница.** Читатель приходит из поиска. Первые строки говорят, что это за страница и для кого она. Условия и контекст повторяются там, где они нужны читателю. Write the Docs называет этот принцип ARID: допустим некоторый повтор в документации. Нормативные факты (значение по умолчанию, лимит, флаг) живут в одном месте, остальные страницы ссылаются туда. Runbook держит свои команды на своей странице.

**Один термин на одно понятие.** Выберите одно слово для каждого понятия, определите его при первом упоминании и не меняйте. Новое слово подсказывает читателю, что речь о новом понятии.

**Связность.** Начинайте предложение с того, что читатель уже знает, и заканчивайте новым. Первое предложение абзаца называет его тему. Заголовок простыми словами передаёт главную мысль раздела.

**Примеры работают.** Каждая команда и каждый фрагмент кода работают в том виде, как написаны, плейсхолдеры помечены (`<NAMESPACE>`). После шага, который может тихо не сработать, покажите, как выглядит успех.

**Актуальность.** Неверная документация хуже отсутствующей. Живой документ с ошибкой исправьте или удалите. Содержание записи не меняйте никогда: напишите новую запись, а старую пометьте как замещённую. Кроме опечаток и битых ссылок, в опубликованную запись вносят только отметку о статусе (`[YANKED]`, `superseded by`) и ссылку на замену. Там, где это важно, укажите, к какой версии относится страница. Избегайте фраз, которые устаревают с датой.

**Числа — ориентиры.** Числа в файлах типов и стиля даны с источником или с пометкой «эмпирика». Жёстких порогов среди них нет.

**Визуальное содержимое.** Картинка нужна только там, где текст справляется хуже: архитектура, поток, интерфейс. Диаграммы держите как код (Mermaid и подобные), чтобы их правили вместе с текстом. Скриншот обрежьте до нужной области, выделите на нём действие, напишите alt-текст и оставьте шаг в тексте. Данные ставьте в таблицу. Подпись говорит, что читатель должен увидеть.

## Порядок работы

Скопируйте этот чек-лист в ответ и отмечайте пункты по ходу:

```
Ход работы над документом:
- [ ] 1. Читатель: кто он, его задача, его состояние
- [ ] 2. Тип выбран; файл типа, файл стиля и каталог паттернов загружены
- [ ] 3. Каркас из файла типа
- [ ] 4. Первый черновик
- [ ] 5. Правка по проходам: структура, абзацы и связность, предложения, слова
- [ ] 6. check.py запущен, все error исправлены, все warning прочитаны
- [ ] 7. Чек-лист типа пройден
- [ ] 8. Проверка холодным читателем пройдена
```

Чек-лист отмечает ход работы в разговоре. В документ для читателя он не попадает, как и любое упоминание этого скилла или его файлов.

**Шаг 5.** Правьте отдельными проходами, от крупного к мелкому. Стивен Кинг в книге «Как писать книги» даёт формулу: второй черновик равен первому минус 10%. Скилл считает её ориентиром.

**Шаг 6.** Запустите проверку из любого каталога:

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/check.py" --lang ru <file>
```

Скрипт находит длинные предложения, стоп-слова, LLM-маркеры, битые ссылки, фразы с датой и нарушения русской типографики. Исправьте каждый `error`. Прочитайте каждый `warning` и либо исправьте текст, либо оставьте его по причине, которую можете назвать.

**Шаг 8.** Дайте черновик холодному читателю вместе с одной задачей читателя: «Ты новый инженер. Пользуясь только этой страницей, разверни сервис на стейдже. Напиши, где застрял или пришлось угадывать». Возьмите субагента без контекста разговора или попросите пользователя показать текст человеку. Исправьте каждое место, где читатель остановился, и снова пройдите шаги 6 и 7.
