# Changelog, release notes и руководство по миграции

Changelog перечисляет заметные изменения каждой версии для тех, кто пользуется проектом. Release notes представляют одну версию широкой аудитории. Руководство по миграции проводит читателя через ломающие изменения между двумя версиями.

## Когда это он и когда нет

Раздел changelog пишут к каждому релизу. Release notes добавляют, когда пользователям нужно больше списка: контекст, главное, скриншоты. Руководство по миграции добавляют, когда ломающее изменение нельзя принять за один шаг.

Выберите другой тип, если:

- нужны причины изменения: ADR, ссылка на него стоит в пункте changelog;
- нужна процедура, не связанная с обновлением: how-to.

## Каркас

Форму файла задаёт Keep a Changelog 1.1.0:

1. Сверху раздел `Unreleased`, в котором копятся изменения до следующего релиза.
2. По разделу на версию, новые сверху, с номером версии и датой релиза в формате ISO 8601: `## [1.4.0] - YYYY-MM-DD`.
3. Внутри версии изменения сгруппированы по видам в таком порядке: Added, Changed, Deprecated, Removed, Fixed, Security.

Этот тип добавляет одно правило для ломающих изменений. Каждое остаётся в своей группе (обычно Changed или Removed) и стоит в ней первым. Пункт начинается с `BREAKING:` и ссылается на руководство по миграции.

Release notes идут в том же порядке: ломающие изменения, потом что читатель получает, потом исправления.

У руководства по миграции свой каркас:

1. С какой версии на какую и кому нужно действовать.
2. Каждое ломающее изменение: что изменилось, что сломается и как адаптироваться, с кодом до и после.
3. Как проверить обновление.

## Голос и глаголы

Changelog пишут для людей. Keep a Changelog говорит об этом так: «Changelogs are for humans, not machines». Каждый пункт говорит, что изменилось для пользователя, в прошедшем времени или именной группой: «Добавлен флаг `--json` для `list`». Шаги руководства по миграции пишутся в повелительном наклонении.

## Объём

Ориентир: одна строка на изменение (эмпирика). Изменению, которому нужен абзац, дайте ссылку на release notes или руководство по миграции.

## Отличия от общих правил

- **Релиз фиксируется как запись.** Общие правила исправляют или удаляют неверный живой документ. Раздел опубликованной версии не переписывают. Если релиз отозвали, Keep a Changelog ставит рядом с версией метку `[YANKED]`; добавьте ссылку на версию, которая его заменяет. Исправление попадает в пункты следующей версии, а старый пункт получает ссылку на неё. Кроме опечаток и битых ссылок, в опубликованную запись вносят только отметку о статусе (`[YANKED]`, `superseded by`) и ссылку на замену.

## Запрещено

- Выгрузка сообщений коммитов или `git log`.
- Пункты, которые описывают правку кода вместо её влияния на пользователя: `Отрефакторен парсер`.
- Даты в любом формате, кроме ISO 8601.
- Ломающее изменение без метки, спрятанное в группе Changed.
- Удаление или переписывание раздела опубликованной версии.

## Чек-лист типа

- [ ] Версии идут от новых к старым, у каждой дата в ISO 8601.
- [ ] Изменения сгруппированы по шести видам в заданном порядке.
- [ ] Каждое ломающее изменение открывает свою группу, начинается с `BREAKING:` и ссылается на руководство по миграции.
- [ ] Каждый пункт говорит о влиянии на пользователя.
- [ ] У опубликованных версий изменены только отметка о статусе и ссылка на замену.
- [ ] Руководство по миграции показывает код до и после и шаг проверки.
