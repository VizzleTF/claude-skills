# План набора документов

## Содержание

- Аудитория
- Инвентаризация
- Friction log
- Минимальный набор
- Приоритет
- Публикация
- Обратная связь и метрики
- Поддержка и списание
- Формат плана

Этот процесс идёт до первой страницы, когда запрос охватывает весь проект, нескольких читателей или аудит документации. Результат — короткий план, который утверждает пользователь. После утверждения каждая страница пишется как отдельный документ одного типа.

## Аудитория

Перечислите читателей. Для каждого напишите одну строку: кто он, зачем пришёл, что уже знает и в каком состоянии приходит. У программного проекта обычно такие читатели: посетитель, который оценивает проект; новый пользователь, который его устанавливает; постоянный пользователь с одной задачей; дежурный; контрибьютор.

Джинни Рэдиш описывает страницу как одну реплику в разговоре: читатель приходит с вопросом, страница на него отвечает. Для каждого читателя запишите вопросы, с которыми он приходит. Из этих вопросов получаются заголовки страниц и разделов.

Если читатели неизвестны, задайте пользователю один вопрос с ответом по умолчанию: «Кто первым прочтёт эту документацию: те, кто оценивает инструмент, или инженеры вашей команды? Если не скажете, буду писать для инженеров команды».

## Инвентаризация

Составьте список того, что уже есть: README, страницы вики, комментарии, runbook, треды в чате, на которые постоянно ссылаются. Для каждого пункта отметьте тип, читателя, верен ли он и когда его последний раз проверяли. Отметьте дубли и страницы, где смешаны несколько типов.

## Friction log

Пройдите основные задачи читателя сами, по возможности в чистом окружении: установка, первый запуск, самая частая задача, самый частый сбой. Отмечайте каждое место, где пришлось угадывать, искать, читать код или спрашивать. На каждое место одна строка: шаг, что произошло, чего не хватило. Инвентаризация показывает, что есть. Friction log показывает, какие страницы нужны читателю, и по нему лучше решать, что писать.

## Минимальный набор

Руководство Google по документации говорит, что небольшой набор свежих и точных документов лучше большого собрания «документации» в разной степени запущенности. Спланируйте самый маленький набор, который покрывает задачи читателя из friction log. Обычный минимум для инструмента: README, один tutorial или быстрый старт, how-to для частых задач, reference по конфигурации и командам. Сервисы в продакшене добавляют runbook на каждый алерт. Записи (ADR, postmortem, changelog) появляются по мере событий.

У каждой запланированной страницы один тип. Если теме нужны два типа, запланируйте две страницы и свяжите их ссылками.

## Приоритет

Упорядочьте страницы по пользе для читателя: сколько читателей упираются в пробел, как часто и чего им это стоит. Первыми идут отсутствующий runbook для алерта, который будит дежурного, и сломанный шаг установки. Последними идут страницы, которые только пересказывают код. Исправить неверную страницу обычно важнее, чем написать новую: неверная страница ведёт читателя по пути, который заканчивается ошибкой.

## Публикация

Решите, где живёт каждая страница и как читатель её находит. Держите документацию рядом с кодом, который она описывает, если оба меняют одни и те же люди: тогда ревью кода может требовать правку документации. Дайте каждой странице постоянный адрес. Ставьте ссылки там, откуда читатель и так начинает: в README, в сообщении об ошибке, в алерте.

## Обратная связь и метрики

Спланируйте, как читатели сообщают о проблемах: шаблон issue, ссылка внизу каждой страницы, канал. В книге *Docs for Developers* (Бхатти и соавторы) измерение входит в процесс документирования, и каждая метрика привязана к цели документации. Выберите одну или две метрики, которые команда может собирать без новых инструментов. Например, число вопросов в поддержку по теме или время, за которое новый пользователь получает первый результат. Одни просмотры страницы не показывают, помогла ли она.

## Поддержка и списание

Назначьте владельца каждой странице. Привяжите проверку к событиям: релиз, изменённый флаг, закрытый инцидент. Когда живая страница перестаёт быть верной, исправьте её или удалите и перенаправьте её адрес. Для записей правило другое: содержание ADR, postmortem или записи в changelog не меняется никогда. Её замещает более новая запись, а старая получает статус «замещена» и ссылку на новую. Кроме опечаток и битых ссылок, в опубликованную запись вносят только отметку о статусе (`[YANKED]`, `superseded by`) и ссылку на замену.

## Формат плана

Покажите план таблицей и дождитесь утверждения, прежде чем писать:

| Страница | Тип | Читатель | Вопрос читателя | Приоритет | Источник фактов |
|---|---|---|---|---|---|
| Установка на Linux | how-to | новый пользователь | Как установить это на мой сервер? | 1 | скрипт установки, конфигурация CI |
